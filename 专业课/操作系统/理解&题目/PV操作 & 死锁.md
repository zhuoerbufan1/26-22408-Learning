## 互斥机制的几种实现

### 软件实现 - 单标志法

单标志法使用了一个变量 turn 作为谦让的动作，即每个进程会在自己的代码中将 turn 设置为另一个进程来表示谦让，也就是说 turn = i 表示第 i 个进程可以访问临界资源了

如下所示：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718171645.png)

在进程 P 0 中将 turn 设置为 1 表示将临界资源的访问权谦让给进程 P 1，同理，在进程 P 1 中将 turn 设置为 0 表示将临界资源的访问权谦让给进程 P 0

它的实现互斥机制的逻辑是，初始时刻 turn = 0 表示进程 P 0 可以访问临界资源，进程 P 0 进入 while 循环，while 循环是用来阻拦进程进入临界区的，这里可以直接跳出 while 循环 P 0 进入临界区

当 P 0 在临界区并发被强行停止然后调度 P 1 进程的时候，P 1 进程虽然可以占用 CPU 并且到了 while 循环执行自己的指令，发现 turn = 0 自己不能进入临界区，所以会一直执行 while 循环被循环拦住，直到自己的时间片用完，然后调度进程 P 0 继续执行临界区，然后将 turn 设置为 1，表示谦让给进程 P 1，此时进程 P 1 才可以进入临界区

这种方式的缺陷在于，当 turn = 0 的时候，P 0 迟迟不访问临界区，此时临界资源是空闲的，但是 turn 始终没有被 P 0 谦让给 P 1，那么 P 1 也无法访问临界区，所以不满足空闲让进的原则

### 软件实现 - 双标志先检查法

这种方式是对单标志法的改进，两个进程各自占用一个变量，每个变量表示了这个进程对于进入临界区的意愿，比如 `flag[0] = true` 就表示 P 0 进程想要进入临界区，while 循环仍然是作为阻拦的作用，while 循环会检查对方的意愿，如果对方有意愿进入临界区，则当前进程被阻拦：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718172844.png)

这样就很好的解决了单标志法不满足空闲让进的原则，同时这个方法实现了互斥访问机制

但是，这种方法无法满足忙则等待的原则，也就是两个进程可能会同时进入临界区；这是因为 while () 这一行没有做到很好的阻拦作用

比如两个进程并发执行，此时两个进程都没有表达自己进入临界区的意愿，P 0 进程执行到 while，没有被阻拦，然后当 P 0 想要设置 flag[0] = true 的时候它突然被暂停，然后调度 P 1 进程执行，P 1 执行到 while 的时候也没有被阻拦，因为 P 0 还没有设置自己的意愿转去执行 P 1 了

然后 P 1 顺利进入临界区，然后又暂停 P 1 调度 P 0 执行，P 0 从 flag[0] = ture 开始执行，也可以顺利进入临界区

这样两个进程就同时可以进入临界区了，显然不满足临界区忙则等待的原则

### 软件实现 - 双标志后检查法

这种方式是对双标志先检查法的简单改进，它将表达进入临界区的意愿放在 while 阻拦的前面：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718183930.png)

这样就不可能会出现两个进程同时进入临界区的现象了，满足了忙则等待的原则

但是，这种方式会导致两个进程都无法进入临界区的现象

比如 P 0 进程执行完第一行指令，表达了自己进入临界区的意愿，接着被暂停去执行 p 1，P 1 执行了第 5 行代码，也表达了自己进入临界区的意愿

但是往后，两者都会被 while 循环阻拦，两个都无法进入临界区，相当于两个卡 bug 被卡死了

这就不满足空闲让进和有限等待的原则了

### 软件实现 - Peterson 算法

这种算法结合了单标志法和双标志后检查法，它用一个 turn 变量来表示进程的谦让，同时用一个变量表示进程的意愿，while 仍然表示阻拦的作用

两个进程在表达了自己的意愿的同时会做一次谦让，如果两者都表达了自己对临界区的意愿，那么遇到 while 被阻拦的时候，最后一次谦让的进程会丧失临界资源的有限访问权

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718184752.png)
执行顺序（1）（2）（3）（6）（7）（8）：
进程 P 0，执行（1）（2），它表达了自己的意愿，但是会谦让一次，虽然谦让，但是 P 1 没有表达自己的意愿，所以执行（3）的时候没有被阻拦，直接进入临界区；
然后进程调度 P 1 执行，（6）（7）它也会表达自己的意愿，同时谦让一次，执行（8）的时候双方都表达了自己的意愿，但是 P 1 是最后谦让的，所以丧失了进入临界区的权限，只能被阻拦卡死

执行顺序（1）（6）（2）（3）
进程 P 0，表达了自己的意愿，然后进程 P 1，表达了自己的意愿，然后进程 P 0 谦让一次，遇到阻拦，由于 P 0 是遇到阻拦前最后一次谦让的，它会被卡死，不能先进入临界区



这个算法很好的实现了空闲让进，忙则等待，有限等待三个原则，但是没有解决让权等待的问题，也就是当进程 P 1 最后一次谦让执行（8）的时候如果临界区是忙的，那么 P 1 会一直卡死在 while 循环中，一直等待自己的时间片用完，而不是直接让出 CPU 的使用权，这个就是忙等

### 硬件实现  - 中断屏蔽方法

由于进程调度需要内核执行，需要通过中断进入内核态

那么一个进程在进入临界区之前直接把中断给关了，那么它在临界区的时候 CPU 就无法调度别的进程了，那它当然就是独占临界区了

但是这种方法不适于多处理机，因为你进程关中断只能关自己正在占据的 CPU 的中断，别的 CPU 的中断还是无法关，别的 CPU 还是可以调度进程来跟你同时访问临界资源

也不适用于用户进程，用户进程掌握了开关中断比较危险

### 硬件实现 - TestAndSet 指令

这个指令用 C 语言的逻辑说明如下：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718190846.png)

首先，这里虽然用 C 语言说明逻辑，但实际上上述指令是由硬件一口气全部执行的，并且不被允许打断

它的输入是一个共享变量 lock

Test 的意思是检查各 lock 变量的旧值，即返回被别的进程设置的旧值
Set 的意思是将 lock 设置成 true，即上锁

TestAndSet 的指令整体的作用就是返回别的进程给 lock 设置的旧值，同时自己给 lock 设置成 ture，即上锁

这样，当遇到 while 阻拦的时候，它会检查 lock 是否被别人上锁，如果别人上锁了，它虽然也会将 lock 上锁，但是返回值是别人被 lock 上的锁，即 true，所以会被 while 卡死，一直到时间片到期，然后转去执行别的进程，别的进程访问完了临界区，给 lock 解锁，设置成 false；然后再调度当前进程执行的时候它返回的就是 false ，然后通过 while，执行自己的临界区代码

while 在这些互斥机制实现中就是检查别人作为阻拦作用的

这种硬件实现可以很好满足忙则等待，空闲让进，有限等待；然是仍然不满足让权等待，对于单 CPU 来说，它仍然会卡死在 while 阻拦上，只能等待自己的时间片用完才会让出 CPU，然后去执行别的进程
### 硬件实现 - Swap 指令

这个指令功能和 TestAndSet 指令是完全一样的，仍然是进程自己维护一个 old 变量，然后 lock 变量是共享的：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718192737.png)

在这个指令中，进程会先将 old 设置为 ture，然后进入一次阻拦循环，在这个循环中执行 swap 指令，这个指令的作用就是交换 lock 变量和 old 的变量的值，其实就是和 TestAndSet 完全一样

将 old 的值赋给 lock，也就是 Set，即就是将 lock 设置为 true，即上锁，同时将 lock 赋值给 old，即 Test，获得别的进程给 lock 设置的值，然后 while 会检查 old，也就是检查别的进程给 lock 设置的值

它的功能与 TestAndSet 完全一样，所以也不满足让权等待的原则

### 互斥锁

互斥锁其实更像是一种方法归纳抽象

它将访问临界区之前和之后的动作同一抽象成获得锁 acquire () 和释放锁 relase () 的动作

获得锁的功能就是**检查别的进程是否得到了锁并进行阻拦，如果别人没有获得锁，则通过阻拦，然后让自己获得锁**

释放锁就是将锁释放，让别的进程可以通过 while 阻拦，然后拿到锁

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718193715.png)

上述是逻辑实现，注意这里也只是逻辑实现，acquire () 和 release () 的功能都必须是原子实现不能被中断，所以一般就由硬件实现

注意这里的 available 是指共享的变量，当然其实这里它只是对获得锁的一种抽象，只能你能够在 acquire () 实现检查别的进程是否得到了锁并进行阻拦，如果别人没有获得锁，则通过 while 阻拦然后让自己获得锁这个功能，那就是互斥锁的 acquire () 实现，就可以称为互斥锁

比如用 TS 指令实现 acquire ()：

```c
acquire(){
	while(TestAndSet(&lock));
}
```

这里 `while(TestAndSet(&lock));` 这行代码就完美实现了检查别人是否获得了锁并进行阻拦，同时如果别人没有获得锁则通过阻拦，然后自己获得锁

虽然跟 acquire () 的传统定义不一样，而且两个共享变量的设置也完全相反，定义中是将 available 设置成 false 获得锁，TS 实现中是将 lock 设置成 true 获得锁；但其实本质是一样的，获得锁本质就是让别的进程卡死在 while 循环上，**只要能让别的进程人卡死在 while 阻拦，这就是当前进程获得锁的动作**

互斥锁的最大缺点就是忙等待，这个上文的说过了不再说

不过在多处理器系统中，一个进程虽然会卡死在 while 阻拦上面，但是，别的，访问临界区的进程此时在别的处理器上运行，所以很可能这个卡死在 while 上的进程时间片中途就可以获得锁然后进入临界区执行，它卡死等待上锁的时间不会很长，所以它听适合多处理器系统的

它的等待只会卡死，不会切换上下文，所以如果等待时间很短，即卡死时间很短，即上锁时间短的话，其实代价也挺少的，尤其是在多 CPU 系统中

记录型信号量主要是对 value 的理解，这里记录型信号量的数据结构定义如下：

**value >= 0 的含义是，在所有进程都没有进行 PV 操作的时候，value 的绝对值表示可以分配的资源数**

**value < 0 的含义是，在所有进程都没有进行 PV 操作的时候，value 的绝对值表示正在等待的进程数**

这里 V 操作之所以加上等号是因为在进入 V 操作之前 value = -1，表示有一个进程处于等待队列，此时当前进程进入 V 操作表示释放了一个资源，value ++ ，那么这个等待的进程就可以得到一个资源了，于是就可以被唤醒使用这个资源了


所以这里的 value 只是表示两种状态，它为负的时候并不意味着被阻塞的进程无法获得资源，它为负，其绝对值只是表示被阻塞等待资源的进程的个数

这样这种基于记录行信号量的 PV 操作，就可以保证在进程无法获得资源的时候直接自我阻塞，即满足了让权等待，而不是像上文的实现一样卡死在那里

## 记录型信号量实现同步机制

同步机制的实现也很简单

假设有两个进程，P 1 的一部分代码 A 必须在 P 2 的一部分代码 B 之前执行，此时只用将信号量 value 设置为 0

然后在 A 之后设置 V 操作，在 B 之前设置 P 操作即可，那么此时“系统资源”天然就是只有 0 份，P 2 的 B 代码之前想要 P 一下获得资源那就是不可能的，只能自己阻塞，然后 value 变成-1

只有 P 1 执行完了 A 之后 V 一下，释放一个系统资源，此时 P 2 进程才能被唤醒继续执行：

## PV 操作分析

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250719155337.png)


**（1）PV 操作无论是在同步问题中还是互斥问题中一定是成对出现的**

**（2）在同步问题中的 PV 操作，更像是进程在某种资源存在前后的约束关系，而不是简单的进程间的行为的严格前后关系**

P 操作是用来检查这种资源是否存在，拿走资源，如果没有则进程阻塞；
V 操作是用来形成这个资源让这个资源存在，放入资源到缓冲区，同时唤醒阻塞的进程

比如生产者和消费者的一对同步关系，消费者必须在缓冲区有产品之后才能取走产品，那这里的资源存在就是产品在缓冲区的存在，消费者必须在资源存在之后才能执行自己的动作，所以消费者进程就得在自己的动作之前执行 P 操作，来检查产品是否存在的情况，这样才能保证自己后续的实际访问资源拿走并消费的动作在产品存在这个状态之后

而 V 操作与这个 P 操作是成对的，它是让这个资源存在，所以当然放在生产者生产并放入产品到缓冲区动作之后

而对于上文那种某个进程 P 2 的动作执行必须在另外一个进程 P 1 执行之后也可以用这里的资源存在来解释，这里其实就是资源存在初始为 0 嘛，P 2 的代码之前放一个 P 操作，初始的时候就没有资源，所以它只能等 P 1 进程执行完代码之后进行 V 操作生产一个资源让资源存在，然后 P 2 的动作代码才能执行，所以就保证了 P 1 的代码动作一定在 P 2 之前了

**（3）资源存在是一个很抽象的东西，它可以指实际的产品存在情况，也可以指空闲资源的存在情况**

比如消费者拿走资源并消费必须在产品存在之后，那这里的资源存在就是产品存在；比如生产者生产资源并放入缓冲，那这里的资源存在就是空闲资源的存在，生产者生产资源并放入缓冲的动作必须在空闲资源存在之后

**（4）资源存在的初值就按照系统初始情况的设置就好，不用考虑太多**

比如生产者 - 消费者问题的产品存在，初始就是 0，因此就设置为 0；空闲资源存在，初始就是 N 个块都空闲，所以设置为 N

**（5）一个资源存在问题对应的是一个同步问题，并且实际上是对应了两类相对的进程，即一类进程需要在资源存在之后，拿走资源；另一类进程则是生产资源保证资源存在，本质还是生产者和消费者问题**

是两类相对的进程而不是两个相对的进程

这两类相对的所有进程的 PV 操作都是对同一个资源进行的，在资源存在之后拿走资源的这类进程全部都是相同的 P 操作；生产资源保证资源存在的这类进程全部都是相同的 V 操作

比如在多个生产者 - 消费者问题中，苹果资源的存在，对应了父亲和女儿的一对关系，父亲是属于生产苹果的这类进程，女儿是拿走苹果的这类进程，这类资源存在同步问题相对的两类进程各只有一个

比如空盘子资源的存在将父母两个进程划分成了同一类，即拿走空盘资源的这类进程；儿女两个进程划分成了同一类，即生产空盘子资源，那么这两类资源就是围绕空盘子资源进行 PV 操作，父母都是 P 操作，是完全一样的 P 操作；儿女都是 V 操作，都是完全一样的 V 操作；这里围绕空盘子资源的同步关系其实就跟生产者消费者问题一样了，儿女进程都是生产空盘子资源的生产者进程，父母都是消费空盘子资源的消费者进程

### 单生产者 - 单消费者，单缓冲，单次取出类问题（最经典的问题）

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250719182923.png)

生产者和消费者问题是最原始的最经典的 PV 操作问题，它包含一个互斥，即各个进程必须互斥访问临界资源；两个同步问题，一个同步问题是产品资源的存在，一个同步问题是空闲资源的存在

所以生产者和消费者问题要有三个信号量来控制

（1）mutex 信号量，用来控制所有的进程互斥访问缓冲区
（2）full 信号量，用来表示缓冲区产品的存在情况，初始是 0
（3）empty 信号量，用来表示缓冲区空闲块的存在情况，初始是 n


首先，对于互斥问题，生产者和消费者以及所有的进程都必须互斥访问缓冲区，所以互斥的 PV 操作每个进程都在进入临界区之前和之后进行，相当于 PV 操作将临界区夹住

对于缓冲区产品存在的同步问题，消费者必须在缓冲区产品存在之后才能取走资源，所以 P (full) 就在消费者从缓冲区取走产品之前，PV 成对出现，V 操作就应该在形成这个资源（缓冲区产品存在）动作之后，因此 V (full) 就放在生产者放入产品到缓冲区动作之后

对于缓冲区空闲资源存在的同步问题，生产者必须在缓冲区空闲块存在的时候才能放入产品到缓冲区，所以 P (empty) 就应该放在生产者放入缓冲区产品动作之前，用来表示检查缓冲区空前块是否存在，PV 成对出现，V (empty) 操作就应该在形成者空闲资源的动作之后，即消费者从缓冲区拿走一个产品的动作之后

这样就可以很轻易的写出下面的代码：

```cpp
int n;                                  // 缓冲区大小
semaphore mutex = 1;                    // 互斥信号量：实现缓冲区的互斥访问
semaphore full = 0;                      // 同步信号量：非空缓冲区数量（产品数）
semaphore empty = n;                     // 同步信号量：空缓冲区数量

void producer() {
    while (true) {                       // 生产者循环
        生产一个产品(数据);               // 生产数据（非临界区操作）
        p(empty);                        // 请求空缓冲区（若无则阻塞）
        p(mutex);                        // 请求进入临界区（互斥访问缓冲区）
        将产品(数据)放入缓冲区;           // 临界区操作：数据放入缓冲区
        v(mutex);                        // 释放临界区
        v(full);                         // 增加一个产品（唤醒等待的消费者）
    }
}

void consumer() {
    while (true) {                       // 消费者循环
        p(full);                         // 请求产品（若无则阻塞）
        p(mutex);                        // 请求进入临界区
        从缓冲区取出数据;                 // 临界区操作：取出数据
        v(mutex);                        // 释放临界区
        v(empty);                        // 释放空缓冲区（唤醒等待的生产者）
        消费产品;                        // 消费数据（非临界区操作）
    }
}
```

需要注意事项：

**（1）mutex 的 P 操作，无论是生产者还是消费者进程，都不能放在 P (empty) 或者 P (full) 操作之前**

因为如果消费者的 P (mutex) 放在 P (full) 之前的话，假如消费者进程先执行，执行 P (mutex)，然后执行 P (full)，发现 full 原本 = 0，自己阻塞等待生产者放入产品到缓冲区；然后转到生产者执行，生产者执行 P (empty) 发现 empty = n 空闲块资源充足，所以继续执行，P (mutex)，发现已经被锁上了，所以生产者又阻塞等待消费者

这样就会导致生产者和消费者互相等待，出现死锁问题

**（2）mutex 的 V 操作可以与 V (empty) 或者 V (full) 两个操作互换**

这是因为 V 操作不会导致进程阻塞

假如生产者的 V (full) 操作在 V (mutex) 的后面；最开始仍然是消费者进程先执行，阻塞在 P (full) 上面

生产者执行 V (full) 之后唤醒了消费者进程，生产者执行完毕 V (full)，然后突然调度去执行消费者的 P (mutex)，虽然消费者仍然会被卡死在这里，但是时间片用完之后生产者继续执行 V (mutex)，这样消费者就被唤醒了，等到生产者执行完了调度消费者执行，消费者同样可以顺利进入临界区

**（3）消费产品的动作最好是放在两个 V 操作的之后；同理生产产品的动作也最好是放在两个 P 操作之前**

理论上来说，消费产品的动作其实放在从缓冲区取走了一个产品之后就行了，但是如果 V (mutex) 或者 V (empty) 在消费产品之后的话会导致临界资源和空闲资源释放太慢，因为你从缓冲区取走一个产品就可以释放临界资源以及释放一个空闲块，从而唤醒别的进程工作了，但是你非要再插入一个消费产品在释放操作 V 之前，这样别的进程还得等你享受完才能获得资源被唤醒，没必要

同理生产产品也是这样的，理论上只用在临界区放入资源动作之前就可以了，但是如果你 P 操作提前就把资源锁定了，那别的进程还得等你慢慢生产资源才能访问临界区以及你提前锁定了一个空闲块，但是在生产产品这个时间没有使用，那这个生产产品的时间就是白白占据资源不使用浪费掉了

### 双生产者 - 单消费者 - 双缓冲区 - 单次取出类问题

有四个同步问题：

        P(mutex_F2);      // 申请F2货架锁

Assembly_Workshop() {

        P(full_F1);      // 申请A零件资源
        P(mutex_F1);     // 申请F1货架锁
        从F1取出A零件;     // 临界区操作

        V(empty_F1);     // 释放F1空位
        
        P(full_F2);      // 申请B零件资源
        P(mutex_F2);     // 申请F2货架锁
        从F2取出B零件;     // 临界区操作

        P(turn_lock);
        
        for(int i=0; i<10; i++) {

            V(mutex);       // 释放缓冲区锁
            V(empty);      // 释放空槽
        }
        
        // 释放连续取特权
        V(turn_lock);
        
        // 可在此处消费10个产品（非临界区）
    }
}

### 读者 - 写者问题（读者优先）

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250814172220.png)

也就是允许多个读者可以同时读，但是只能有一个写者进行写操作

这个问题需要一个变量 count 来记录访问文件的读者的数量，并且此时 count 也变成了临界资源，需要互斥访问

另外一个互斥关系是写者和读者写者的文件访问互斥

这里没有同步关系，count 变量是用来处理这里的条件关系的，他不是互斥量

因此就是两个互斥信号量：

```
semaphore mutex = 1;//用来对count 进行互斥访问
semaphore mutexSW = 1;//用来写者与读者和写着进行互斥访问文件

int count = 0;//用来记录访问文件的读者个数
```

首先，读者进程在读文件之前需要修改 count 变量的值，所以会在 reading 操作前后进行互斥修改 count 变量：

```c
reader(){
	P(mutex);
	count ++;
	V(mutex);
	
	reading;
	
	P(mutex);
	count --;
	V(mutex);
}
```

然后是读者与写着的互斥问题，这里需要用到信号量 mutexSW，这个信号量的 PV 操作不能简单加到 reading 的前后，因为如果这样做了，那么读者之间也变成互斥访问文件了，这个与题意不符，所以这里也就是 count 变量的作用了，为了保证读者与写者进行互斥，用 count 变量来判断此时是否可能有写者访问文件：

```
reader(){
	P(mutex);
	//如果此时文件区没有读者，说明此时写者可能访问文件，此时需要进行互斥
	if(count == 0){
	//count用来表示当前有多少个进程在读，如果是第一个进程的话，此时还没读呢，所以if语句应该放在count ++前面
		P(mutexSW);
	}
	//如果此时文件区有读者，说明不可能写者正在访问文件，那么此时读者直接修改count进入文件区即可	
	count ++;
	V(mutex);

	reading;

	P(mutex);
	count --;
	//如果是最后一个进程，此时进程都读完了，所以if应该放在count--后面
	if(count == 0){
		V(mutexSW);//最后一个读进程走的时候才会解锁，此时允许写进程进去写数据
	}
	V(mutex);
}
```


简而言之，就是第一个读进程敲门要读的时候会加锁，这样其他的读进程可以来读文明，但是写进程不行

等到所有的进程读完之后，某个进程发现自己是最后一个读的进程，这个时候才会解锁，允许写进程进来写数据

**第一个读进程来的时候要加锁，最后一个读进程走的时候要解锁**

对于写进程来说，他不需要通过 count 变量来判断文件里面是否有读进程或者写进程，他统一用 mutexSW 这个互斥信号量来判断，因为第一个进程进去的时候会加锁，这样写进程再 P (mutexSW) 就知道有读进程在文件里面了，最后一个读进程走的时候解锁，这样写进程就可以用不必卡死了

同时写进程之间也可以用 mutexSW 这个信号量来完成互斥操作，因此写进程就非常简单了，只用 mutexSW 即可

```
write(){
	P(mutexSW);
	
	writing;
	
	V(mutexSW);
}
```

### 读者 - 写者问题（写者优先）


![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250814172220.png)

也就是允许多个读者可以同时读，但是只能有一个写者进行写操作，除此之外

上文的读者优先，如果一直有读者来读的话，这就会导致先到来的写者一直等待读者读完，这就可能导致写者被饿死

要想让写者优先，那么就需要做到，当一些读进程在读的时候，如果此时来了一个写进程，这个写进程会被阻塞，然后写进程后面再过来的读进程，他们必须要等到写进程写完之后再进行读

也就是说，在写进程之前到来的读进程可以进行读，而写进程来了之后同样会等他们退出文件，但是在写进程后面来的读进程，必须等到写进程写完之后才能进行读

要想做到上面类似的排队功能，这里必须要用到另外一个信号量 mutexQ

这个信号量的初值和 PV 操作位置直接当个结论记住，这里只分析他是怎么实现满足题意操作的

```
reader(){
	P(mutexQ);//最开始加上一个P操作
	
	P(mutex);
	if(count == 0){
		P(mutexSW);
	}
	count ++;
	V(mutex);
	
	V(mutexQ);//reading之前加上一个V操作
	
	reading;

	P(mutex);
	count --;

	if(count == 0){
		V(mutexSW);
	}
	V(mutex);
}
```

```c
writer(){
	P(mutexQ);
	P(mutexSW);
	
	writing;
	
	V(mutexSW);
	V(mutexQ);//这里V(mutexQ)和V(mutexSW)的位置无所谓，不过最好是对称写，PV操作将里面的东西包住
}
```

对于连续的读进程来说，他虽然会在最开始 P (mutexQ) 上锁，导致其他的读进程卡死在这里，但是他在 reading 之前会开锁，这样其他的读进程同样可以被唤醒进入文件进行同时读，并不违反允许多个读进程同时读文件的要求

对于写进程来说，考虑先来了几个读进程，在来了一个写进程，再来了一个读进程的情况

这些先到的读进程会进行 P (mutexSW) 操作，这样写进程就无法进入文件写了，但是写进程可以通过 P (mutexQ)，因为这些读进程会在读操作之前释放 mutexQ 信号量，此时写进程会卡死在 P (mutexSW) 而不是 P (mutexQ)

对于写进程之后到来的读进程，由于写进程进行了 P (mutexQ) 操作，所以这些读进程会卡死在最开始的 P (mutexQ) 上，这些后到来的读进程只有等到写进程写完之后进行 V (mutexQ) 操作释放 mutexQ 变量，此时这些读进程才能继续进行然后读文件

这样就实现了比写进程后来的读进程一定在写进程之后进入文件的要求了，写进程就不会被饿死了
