## 互斥机制的软件实现

### 软件实现的含义以及四个原则含义

软件实现的意思就是不同的进程通过在自己的程序中设置一些代码来确保临界区的访问满足下面四个原则：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20251019195218.png)

在软件实现中并没有哪一段程序代码必须放在一起一口气执行的说法

### 软件实现 - 单标志法

单标志法使用了一个变量 turn 作为谦让的动作，即每个进程会在自己的代码中将 turn 设置为另一个进程来表示谦让，也就是说 turn = i 表示第 i 个进程可以访问临界资源了

如下所示：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718171645.png)

在进程 P 0 中将 turn 设置为 1 表示将临界资源的访问权谦让给进程 P 1，同理，在进程 P 1 中将 turn 设置为 0 表示将临界资源的访问权谦让给进程 P 0

它的实现互斥机制的逻辑是，初始时刻 turn = 0 表示进程 P 0 可以访问临界资源，进程 P 0 进入 while 循环，while 循环是用来阻拦进程进入临界区的，这里可以直接跳出 while 循环 P 0 进入临界区

当 P 0 在临界区并发被强行停止然后调度 P 1 进程的时候，P 1 进程虽然可以占用 CPU 并且到了 while 循环执行自己的指令，发现 turn = 0 自己不能进入临界区，所以会一直执行 while 循环被循环拦住，直到自己的时间片用完，然后调度进程 P 0 继续执行临界区，然后将 turn 设置为 1，表示谦让给进程 P 1，此时进程 P 1 才可以进入临界区

这种方式的缺陷在于，当 turn = 0 的时候，P 0 迟迟不访问临界区，此时临界资源是空闲的，但是 turn 始终没有被 P 0 谦让给 P 1，那么 P 1 也无法访问临界区，所以不满足空闲让进的原则

### 软件实现 - 双标志先检查法

这种方式是对单标志法的改进，两个进程各自占用一个变量，每个变量表示了这个进程对于进入临界区的意愿，比如 `flag[0] = true` 就表示 P 0 进程想要进入临界区，while 循环仍然是作为阻拦的作用，while 循环会检查对方的意愿，如果对方有意愿进入临界区，则当前进程被阻拦：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718172844.png)

这样就很好的解决了单标志法不满足空闲让进的原则，同时这个方法实现了互斥访问机制

但是，这种方法无法满足忙则等待的原则，也就是两个进程可能会同时进入临界区；这是因为 while () 这一行没有做到很好的阻拦作用

比如两个进程并发执行，此时两个进程都没有表达自己进入临界区的意愿，P 0 进程执行到 while，没有被阻拦，然后当 P 0 想要设置 flag[0] = true 的时候它突然被暂停，然后调度 P 1 进程执行，P 1 执行到 while 的时候也没有被阻拦，因为 P 0 还没有设置自己的意愿转去执行 P 1 了

然后 P 1 顺利进入临界区，然后又暂停 P 1 调度 P 0 执行，P 0 从 flag[0] = ture 开始执行，也可以顺利进入临界区

这样两个进程就同时可以进入临界区了，显然不满足临界区忙则等待的原则

**这种方式不能实现互斥机制**
### 软件实现 - 双标志后检查法

这种方式是对双标志先检查法的简单改进，它将表达进入临界区的意愿放在 while 阻拦的前面：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718183930.png)

这样就不可能会出现两个进程同时进入临界区的现象了，满足了忙则等待的原则

但是，这种方式会导致两个进程都无法进入临界区的现象

比如 P 0 进程执行完第一行指令，表达了自己进入临界区的意愿，接着被暂停去执行 p 1，P 1 执行了第 5 行代码，也表达了自己进入临界区的意愿

但是往后，两者都会被 while 循环阻拦，两个都无法进入临界区，相当于两个卡 bug 被卡死了

这就不满足空闲让进和有限等待的原则了

**这种方式会让两个进制饥饿**
### 软件实现 - Peterson 算法

这种算法结合了单标志法和双标志后检查法，它用一个 turn 变量来表示进程的谦让，同时用一个变量表示进程的意愿，while 仍然表示阻拦的作用

两个进程在表达了自己的意愿的同时会做一次谦让，如果两者都表达了自己对临界区的意愿，那么遇到 while 被阻拦的时候，最后一次谦让的进程会丧失临界资源的有限访问权

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718184752.png)
执行顺序（1）（2）（3）（6）（7）（8）：
进程 P 0，执行（1）（2），它表达了自己的意愿，但是会谦让一次，虽然谦让，但是 P 1 没有表达自己的意愿，所以执行（3）的时候没有被阻拦，直接进入临界区；
然后进程调度 P 1 执行，（6）（7）它也会表达自己的意愿，同时谦让一次，执行（8）的时候双方都表达了自己的意愿，但是 P 1 是最后谦让的，所以丧失了进入临界区的权限，只能被阻拦卡死

执行顺序（1）（6）（2）（3）
进程 P 0，表达了自己的意愿，然后进程 P 1，表达了自己的意愿，然后进程 P 0 谦让一次，遇到阻拦，由于 P 0 是遇到阻拦前最后一次谦让的，它会被卡死，不能先进入临界区



这个算法很好的实现了空闲让进，忙则等待，有限等待三个原则，但是没有解决让权等待的问题，也就是当进程 P 1 最后一次谦让执行（8）的时候如果临界区是忙的，那么 P 1 会一直卡死在 while 循环中，一直等待自己的时间片用完，而不是直接让出 CPU 的使用权，这个就是忙等

## 互斥机制的硬件实现

硬件实现的含义是不同的进程通过一些硬件操作保证临界区的访问满足下面四个原则：

![](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20251019195218.png)

这些进程执行的硬件操作在下文中按照C语言的形式给出，但是他们需要一口气全部执行完毕，是为原子操作
### 硬件实现  - 中断屏蔽方法

由于进程调度需要内核执行，需要通过中断进入内核态

那么一个进程在进入临界区之前直接把中断给关了，那么它在临界区的时候 CPU 就无法调度别的进程了，那它当然就是独占临界区了

但是这种方法不适于多处理机，因为你进程关中断只能关自己正在占据的 CPU 的中断，别的 CPU 的中断还是无法关，别的 CPU 还是可以调度进程来跟你同时访问临界资源

也不适用于用户进程，用户进程掌握了开关中断比较危险

### 硬件实现 - TestAndSet 指令

这个指令用 C 语言的逻辑说明如下：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718190846.png)

**首先，这里虽然用 C 语言说明逻辑，但实际上上述指令是由硬件一口气全部执行的，并且不被允许打断**，上图右边就是进程利用TestAndSet指令实现的临界区访问示例

它的输入是一个共享变量 lock

Test 的意思是检查各 lock 变量的旧值，即返回被别的进程设置的旧值
Set 的意思是将 lock 设置成 true，即上锁

TestAndSet 的指令整体的作用就是返回别的进程给 lock 设置的旧值，同时自己给 lock 设置成 ture，即上锁

这样，当遇到 while 阻拦的时候，它会检查 lock 是否被别人上锁，如果别人上锁了，它虽然也会将 lock 上锁，但是返回值是别人被 lock 上的锁，即 true，所以会被 while 卡死，一直到时间片到期，然后转去执行别的进程，别的进程访问完了临界区，给 lock 解锁，设置成 false；然后再调度当前进程执行的时候它返回的就是 false ，然后通过 while，执行自己的临界区代码

while 在这些互斥机制实现中就是检查别人作为阻拦作用的

这种硬件实现可以很好满足忙则等待，空闲让进，有限等待；然是仍然不满足让权等待，对于单 CPU 来说，它仍然会卡死在 while 阻拦上，只能等待自己的时间片用完才会让出 CPU，然后去执行别的进程
### 硬件实现 - Swap 指令

这个指令功能和 TestAndSet 指令是完全一样的，仍然是进程自己维护一个 old 变量，然后 lock 变量是共享的：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718192737.png)

在这个指令中，进程会先将 old 设置为 ture，然后进入一次阻拦循环，在这个循环中执行 swap 指令，这个指令的作用就是交换 lock 变量和 old 的变量的值，其实就是和 TestAndSet 完全一样

将 old 的值赋给 lock，也就是 Set，即就是将 lock 设置为 true，即上锁，同时将 lock 赋值给 old，即 Test，获得别的进程给 lock 设置的值，然后 while 会检查 old，也就是检查别的进程给 lock 设置的值

它的功能与 TestAndSet 完全一样，所以也不满足让权等待的原则

## 锁
### 锁是什么？

（1）锁其实是一种定义的数据结构，对于进程来说，只有第一个获得锁的进程才可以进入临界区，其他进程必须等待
（2）锁更像是对上文的进程互斥进入临界区动作的归纳，包括一个申请锁的动作，释放锁的动作，以及锁有关的数据结构
![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20251111110813.png)

### 锁分为哪两类？

（1）自旋锁，进程申请锁失败会一直申请，卡死在 while 循环，直到成功，上文的各种例子基本上都属于自旋锁
（2）无忙等待锁，进程申请锁失败会阻塞，释放掉 CPU

### TSL 指令实现无忙等待锁的例子是什么？


这里将自旋锁中的循环等待改成进程阻塞即可，同时在退出临界区的时候唤醒进程

## 管程

### 管程是什么？

其实就是用高级语言实现进程之间的同步与互斥

### 管程包含哪两个主要的功能？

（1）互斥访问：确保不同的线程对共享变量的互斥访问，同一时间只能有一个线程访问共享资源
（2）条件等待和通知：线程可以通过条件变量等待满足某个条件之后继续执行；或者通过条件变量通知其他线程某个条件已经满足
![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20251111145205.png)

### 管程的组成部分有哪些？

（1）共享变量，管程实现了对共享变量的封装，多个进程需要通过管程访问共享变量
（2）互斥锁，用来确保同一时间只能有一个进程访问共享变量，实际上就是管程对于上文互斥锁的模拟
（3）条件变量，它是管程实现的一种机制，线程通过条件变量在条件不足的时候进行等待；同时，通过条件变量在条件满足的时候唤醒通知别的进程
（4）管程接口，管程暴露给外部调用管程所实现的方法的接口

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20251111150417.png)

### 管程实现消费者生产者同步的例子

```cpp
class Monitor{
	int n, count;//共享变量count以及共享变量的最大值n
	Condition producer, consumer;//条件变量，这些条件变量也是一些类，用来提供等待和通知的方法
	Lock lock;//互斥锁

	//管程是一个大类，这个大类中实现了基本的生产和消费方法，用于外部进程调用
	//外部的进程可以直接调用这些方法来实现同步和互斥
	void produce(){
			
		Lock.getlock();//加锁避免别的进程进入临界区
		if(count == n)
			producer.wait(lock);//如果缓冲区满了，则调用条件变量让自己等待
			//这里wait操作必须将lock锁也传过去，因为wait还包括调度操作，在调度别的进程之前自己必须释放这个锁
		count ++;
		consumer.signal();//生产完了，通知消费者进程
		Lock.release();//释放锁，让别的进程可以访问共享变量
	}
	
	void consumer(){
		Lock.getlock();
		if(count == 0)
			consumer.wait(lock);
		count --;
		producer.signal();
		Lock.release();
	}
	
	//条件变量的实现
	class Condition{
		int num;//这个数字表示当前处于阻塞队列的进程数量多少个
		queue<> bolckq;//条件变量所对应的阻塞队列
		
		//wait方法实现
		void wait(Lock lock){
			num ++;//进入阻塞态队列的进程个数加一
			将进程加入到blockq队列中;
			//这里在将当前线程阻塞，调度别的进程执行的时候必须释放锁，否则别的进程无法访问管程中的共享变量了
			lock.release();
			进程调度，调度别的进程执行;
			//被唤醒后再拿到锁
			lock.getlock();
		}

			if(num > 0){
				唤醒一个进程;
				num --;
			}
		}
		//signal这里没有锁的问题，因为signal调用完毕之后回到consumer()函数中，就会直接将锁释放了
		//锁释放了之后回到别的被唤醒的进程，这个进程被唤醒后拿到锁，可以重新进入临界区了
	}
```

## 互斥机制的信号量实现
### 信号量实现 - 记录型信号量

先介绍一下什么是记录型信号量

记录型信号量主要是对 value 的理解，这里记录型信号量的数据结构定义如下：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718203410.png)

关键是对 value，value 其实表示的是一种状态

**value >= 0 的含义是，在所有进程都没有进行 PV 操作的时候，value 的绝对值表示可以分配的资源数**

**value < 0 的含义是，在所有进程都没有进行 PV 操作的时候，value 的绝对值表示正在等待的进程数**

以上两个当作结论记住

那么 PV 操作就比较容易理解了：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718203614.png)
**上图两边对S的更改操作必须是原子化的，不允许中断**（2021年真题），实际上这里的变量S也是临界资源，不同的变量就利用这个变量S来进行临界区的访问，实际上这种方式有点像硬件和软件结合的方式

这里 P 操作之所以不加等号是因为在进入 P 操作之前 value = 1，表示还剩下一个资源，然后这个进程进入 P 操作，value --，表示资源分配给了它，所以进行判断的时候 value = 0，但是它仍然分配到了资源，可以进入临界区

这里 V 操作之所以加上等号是因为在进入 V 操作之前 value = -1，表示有一个进程处于等待队列，此时当前进程进入 V 操作表示释放了一个资源，value ++ ，那么这个等待的进程就可以得到一个资源了，于是就可以被唤醒使用这个资源了


所以这里的 value 只是表示两种状态，它为负的时候并不意味着被阻塞的进程无法获得资源，它为负，其绝对值只是表示被阻塞等待资源的进程的个数

这样这种基于记录行信号量的 PV 操作，就可以保证在进程无法获得资源的时候直接自我阻塞，即满足了让权等待，而不是像上文的实现一样卡死在那里

上文是对记录型信号量的介绍

### 记录型信号量实现同步机制

同步机制的实现也很简单

假设有两个进程，P 1 的一部分代码 A 必须在 P 2 的一部分代码 B 之前执行，此时只用将信号量 value 设置为 0

然后在 A 之后设置 V 操作，在 B 之前设置 P 操作即可，那么此时“系统资源”天然就是只有 0 份，P 2 的 B 代码之前想要 P 一下获得资源那就是不可能的，只能自己阻塞，然后 value 变成-1

只有 P 1 执行完了 A 之后 V 一下，释放一个系统资源，此时 P 2 进程才能被唤醒继续执行：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718212117.png)

对于多个层级，多个进程的多个代码之间的同步也非常简单，如下所示：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718212216.png)

上图的 S 1 和 S 6 分别表示不同进程的不同代码，这些代码的执行必须按照上图所示的顺序执行

我们只需要满足上图任意相邻一对前驱关系顺序就行了，如果任意一对相邻的前后关系都满足了，那其他的前后关系，比如 S 1 和 S 6 的前后关系就天然满足了，因为当满足了任意相邻的前后关系之后，S 6 就不可能会处于 S 2 之前执行，因为 S 6 必须在 S 1, S 5, S 3 之后执行，而 S 1 和 S 5 必须在 S 2 之后执行，所以 S 6 也就必须在 S 2 之后执行了

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250718212821.png)

这样就完美保证了每一对相邻前后代码的执行顺序

注意你每个进程中的代码之后的一堆 V 操作，以及代码之前的一堆 P 操作，这些 V 操作或者 P 操作之间的顺序是无所谓的，比如 P 1 进程，你无论是先对 a 信号量 V 操作还是先对 b 信号量 V 操作，都不会改变每一对相邻代码之间的执行顺序，都不会改变此时 S 1 在 S 2 和 S 3 之前执行的事实（其他的就更不用多说），只要这个不改变，那整个上述流程图的代码执行顺序就是正确的

## PV 操作分析

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250719155337.png)


**（1）PV 操作无论是在同步问题中还是互斥问题中一定是成对出现的**

**（2）在同步问题中的 PV 操作，更像是进程在某种资源存在前后的约束关系，而不是简单的进程间的行为的严格前后关系**

P 操作是用来检查这种资源是否存在，拿走资源，如果没有则进程阻塞；
V 操作是用来形成这个资源让这个资源存在，放入资源到缓冲区，同时唤醒阻塞的进程

比如生产者和消费者的一对同步关系，消费者必须在缓冲区有产品之后才能取走产品，那这里的资源存在就是产品在缓冲区的存在，消费者必须在资源存在之后才能执行自己的动作，所以消费者进程就得在自己的动作之前执行 P 操作，来检查产品是否存在的情况，这样才能保证自己后续的实际访问资源拿走并消费的动作在产品存在这个状态之后

而 V 操作与这个 P 操作是成对的，它是让这个资源存在，所以当然放在生产者生产并放入产品到缓冲区动作之后

而对于上文那种某个进程 P 2 的动作执行必须在另外一个进程 P 1 执行之后也可以用这里的资源存在来解释，这里其实就是资源存在初始为 0 嘛，P 2 的代码之前放一个 P 操作，初始的时候就没有资源，所以它只能等 P 1 进程执行完代码之后进行 V 操作生产一个资源让资源存在，然后 P 2 的动作代码才能执行，所以就保证了 P 1 的代码动作一定在 P 2 之前了

**（3）资源存在是一个很抽象的东西，它可以指实际的产品存在情况，也可以指空闲资源的存在情况**

比如消费者拿走资源并消费必须在产品存在之后，那这里的资源存在就是产品存在；比如生产者生产资源并放入缓冲，那这里的资源存在就是空闲资源的存在，生产者生产资源并放入缓冲的动作必须在空闲资源存在之后

**（4）资源存在的初值就按照系统初始情况的设置就好，不用考虑太多**

比如生产者 - 消费者问题的产品存在，初始就是 0，因此就设置为 0；空闲资源存在，初始就是 N 个块都空闲，所以设置为 N

**（5）一个资源存在问题对应的是一个同步问题，并且实际上是对应了两类相对的进程，即一类进程需要在资源存在之后，拿走资源；另一类进程则是生产资源保证资源存在，本质还是生产者和消费者问题**

是两类相对的进程而不是两个相对的进程

这两类相对的所有进程的 PV 操作都是对同一个资源进行的，在资源存在之后拿走资源的这类进程全部都是相同的 P 操作；生产资源保证资源存在的这类进程全部都是相同的 V 操作

比如在多个生产者 - 消费者问题中，苹果资源的存在，对应了父亲和女儿的一对关系，父亲是属于生产苹果的这类进程，女儿是拿走苹果的这类进程，这类资源存在同步问题相对的两类进程各只有一个

比如空盘子资源的存在将父母两个进程划分成了同一类，即拿走空盘资源的这类进程；儿女两个进程划分成了同一类，即生产空盘子资源，那么这两类资源就是围绕空盘子资源进行 PV 操作，父母都是 P 操作，是完全一样的 P 操作；儿女都是 V 操作，都是完全一样的 V 操作；这里围绕空盘子资源的同步关系其实就跟生产者消费者问题一样了，儿女进程都是生产空盘子资源的生产者进程，父母都是消费空盘子资源的消费者进程

### 单生产者 - 单消费者，单缓冲，单次取出类问题（最经典的问题）

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250719182923.png)

生产者和消费者问题是最原始的最经典的 PV 操作问题，它包含一个互斥，即各个进程必须互斥访问临界资源；两个同步问题，一个同步问题是产品资源的存在，一个同步问题是空闲资源的存在

所以生产者和消费者问题要有三个信号量来控制

（1）mutex 信号量，用来控制所有的进程互斥访问缓冲区
（2）full 信号量，用来表示缓冲区产品的存在情况，初始是 0
（3）empty 信号量，用来表示缓冲区空闲块的存在情况，初始是 n


首先，对于互斥问题，生产者和消费者以及所有的进程都必须互斥访问缓冲区，所以互斥的 PV 操作每个进程都在进入临界区之前和之后进行，相当于 PV 操作将临界区夹住

对于缓冲区产品存在的同步问题，消费者必须在缓冲区产品存在之后才能取走资源，所以 P (full) 就在消费者从缓冲区取走产品之前，PV 成对出现，V 操作就应该在形成这个资源（缓冲区产品存在）动作之后，因此 V (full) 就放在生产者放入产品到缓冲区动作之后

对于缓冲区空闲资源存在的同步问题，生产者必须在缓冲区空闲块存在的时候才能放入产品到缓冲区，所以 P (empty) 就应该放在生产者放入缓冲区产品动作之前，用来表示检查缓冲区空前块是否存在，PV 成对出现，V (empty) 操作就应该在形成者空闲资源的动作之后，即消费者从缓冲区拿走一个产品的动作之后

这样就可以很轻易的写出下面的代码：

```cpp
int n;                                  // 缓冲区大小
semaphore mutex = 1;                    // 互斥信号量：实现缓冲区的互斥访问
semaphore full = 0;                      // 同步信号量：非空缓冲区数量（产品数）
semaphore empty = n;                     // 同步信号量：空缓冲区数量

void producer() {
    while (true) {                       // 生产者循环
        生产一个产品(数据);               // 生产数据（非临界区操作）
        p(empty);                        // 请求空缓冲区（若无则阻塞）
        p(mutex);                        // 请求进入临界区（互斥访问缓冲区）
        将产品(数据)放入缓冲区;           // 临界区操作：数据放入缓冲区
        v(mutex);                        // 释放临界区
        v(full);                         // 增加一个产品（唤醒等待的消费者）
    }
}

void consumer() {
    while (true) {                       // 消费者循环
        p(full);                         // 请求产品（若无则阻塞）
        p(mutex);                        // 请求进入临界区
        从缓冲区取出数据;                 // 临界区操作：取出数据
        v(mutex);                        // 释放临界区
        v(empty);                        // 释放空缓冲区（唤醒等待的生产者）
        消费产品;                        // 消费数据（非临界区操作）
    }
}
```

需要注意事项：

**（1）mutex 的 P 操作，无论是生产者还是消费者进程，都不能放在 P (empty) 或者 P (full) 操作之前**

因为如果消费者的 P (mutex) 放在 P (full) 之前的话，假如消费者进程先执行，执行 P (mutex)，然后执行 P (full)，发现 full 原本 = 0，自己阻塞等待生产者放入产品到缓冲区；然后转到生产者执行，生产者执行 P (empty) 发现 empty = n 空闲块资源充足，所以继续执行，P (mutex)，发现已经被锁上了，所以生产者又阻塞等待消费者

这样就会导致生产者和消费者互相等待，出现死锁问题

**（2）mutex 的 V 操作可以与 V (empty) 或者 V (full) 两个操作互换**

这是因为 V 操作不会导致进程阻塞

假如生产者的 V (full) 操作在 V (mutex) 的后面；最开始仍然是消费者进程先执行，阻塞在 P (full) 上面

生产者执行 V (full) 之后唤醒了消费者进程，生产者执行完毕 V (full)，然后突然调度去执行消费者的 P (mutex)，虽然消费者仍然会被卡死在这里，但是时间片用完之后生产者继续执行 V (mutex)，这样消费者就被唤醒了，等到生产者执行完了调度消费者执行，消费者同样可以顺利进入临界区

**（3）消费产品的动作最好是放在两个 V 操作的之后；同理生产产品的动作也最好是放在两个 P 操作之前**

理论上来说，消费产品的动作其实放在从缓冲区取走了一个产品之后就行了，但是如果 V (mutex) 或者 V (empty) 在消费产品之后的话会导致临界资源和空闲资源释放太慢，因为你从缓冲区取走一个产品就可以释放临界资源以及释放一个空闲块，从而唤醒别的进程工作了，但是你非要再插入一个消费产品在释放操作 V 之前，这样别的进程还得等你享受完才能获得资源被唤醒，没必要

同理生产产品也是这样的，理论上只用在临界区放入资源动作之前就可以了，但是如果你 P 操作提前就把资源锁定了，那别的进程还得等你慢慢生产资源才能访问临界区以及你提前锁定了一个空闲块，但是在生产产品这个时间没有使用，那这个生产产品的时间就是白白占据资源不使用浪费掉了


### 双生产者 - 双消费者，单缓冲区，单取出类问题

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250722174121.png)

这个问题涉及三个同步资源：

（1）空闲盘子资源，这个资源存在将进程分为了两类，一类是父母进程，消费空闲盘子资源；一类是子女进程，产生空闲盘子资源

（2）苹果资源，这个资源只涉及父进程和女儿进程，父进程产生这个苹果资源，女儿进程消费这个苹果资源

（3）橘子资源，这个资源只涉及母进程和儿子进程，母亲进程产生橘子资源，儿子进程消费橘子资源

同样涉及一个互斥问题：

所有进程不能同时访问盘子


所以有三个同步信号量，plate, apple, orange

一个互斥信号量，mutex

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250722174849.png)


```c
// 父亲进程 (生产者-苹果)
dad (){
    while(1){
        准备一个苹果;
        P(plate);      // 申请空盘子资源
        P(mutex);      // 申请临界区锁
        把苹果放入盘子;
        V(mutex);      // 释放临界区锁
        V(apple);      // 增加苹果资源计数
    }
}

// 母亲进程 (生产者-橘子)
mom (){
    while(1){
        准备一个橘子;
        P(plate);      // 申请空盘子资源
        P(mutex);      // 申请临界区锁
        把橘子放入盘子;
        V(mutex);      // 释放临界区锁
        V(orange);     // 增加橘子资源计数
    }
}

// 女儿进程 (消费者-苹果)
daughter (){
    while(1){
        P(apple);      // 申请苹果资源
        P(mutex);      // 申请临界区锁
        从盘中取出苹果;
        V(mutex);      // 释放临界区锁
        V(plate);      // 释放空盘子资源
        吃掉苹果;
    }
}

// 儿子进程 (消费者-橘子)
son (){
    while(1){
        P(orange);     // 申请橘子资源
        P(mutex);      // 申请临界区锁
        从盘中取出橘子;
        V(mutex);      // 释放临界区锁
        V(plate);      // 释放空盘子资源
        吃掉橘子;
    }
}
```

这个问题本质上还是消费者问题，唯一需要注意的是空闲盘子这个资源虽然涉及的是四个进程，但是这四个进程其实只有两类，父母进程消费空闲盘子资源是一类，儿女进程生产空闲盘子资源是一类，同一类进程互相之前的 P 操作或者 V 操作都是相同的

### 双生产者 - 单消费者 - 双缓冲区 - 单次取出类问题

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250722181921.png)

这里有两个互斥问题：

（1）A 车间和装配车间不能同时访问 F 1
（2）B 车间和装配车间不能同时访问 F 2

有四个同步问题：

（1）产品 A 资源存在引起的同步，装配车间必须在 F 1 有了 A 资源之后才能拿走
（2）F 1 空闲资源存在引起的同步，A 车间必须等到 F 1 空闲了才能放入 A 产品
（3）产品 B 资源存在引起的同步，装配车间必须在 F 2 有了 B 资源之后才能拿走
（4）F 2 空闲资源存在引起的同步，B 车间必须等到 F 2 空闲了才能放入 B 产品


因此需要 6 个信号量：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250722183229.png)


A 车间的代码如下：

```c
A_Workshop() {
    while(1) {
        生产一个A零件;
        P(empty_F1);      // 申请F1空位
        P(mutex_F1);      // 申请F1货架锁
        将A放入货架F1;     // 临界区操作
        V(mutex_F1);      // 释放F1货架锁
        V(full_F1);       // 增加F1零件计数
    }
}
```

B 车间的代码如下：

```c
B_Workshop() {
    while(1) {
        生产一个B零件;
        P(empty_F2);      // 申请F2空位
        P(mutex_F2);      // 申请F2货架锁
        将B放入货架F2;     // 临界区操作
        V(mutex_F2);      // 释放F2货架锁
        V(full_F2);       // 增加F2零件计数
    }
}
```

装配车间的代码如下：

```c
Assembly_Workshop() {
    while(1) {
        P(full_F1);      // 申请A零件资源
        P(mutex_F1);     // 申请F1货架锁
        从F1取出A零件;     // 临界区操作
        V(mutex_F1);     // 释放F1货架锁
        V(empty_F1);     // 释放F1空位
        
        P(full_F2);      // 申请B零件资源
        P(mutex_F2);     // 申请F2货架锁
        从F2取出B零件;     // 临界区操作
        V(mutex_F2);     // 释放F2货架锁
        V(empty_F2);     // 释放F2空位
        
        组装A+B为产品;     // 非临界区操作
    }
}
```

在装配车间的代码中 `P(full_F2)` 它的位置可以紧接着放在 `P(full_F1)` 之后，调换了一下顺序整个系统的代码也是正确的，因为缓冲 F 2 涉及的互斥和同步与缓冲 F 1 涉及的互斥与同步时完全独立的，信号量也是独立的，只要你能保证单个缓冲涉及的互斥和同步是正确的，那么每个缓冲区涉及的同步与互斥问题之间的代码顺序是随意的

你甚至可以将 `P(full_F2)` 直接放在装配车间的临界区代码中，虽然装配进程会阻塞在访问 F 1 的临界区，但是 B 车间仍然可以访问 F 2，仍然可以生产 B 产品放入 F 2 然后唤醒装配进程，并不会出现死锁的现象，这种代码顺序只可能影响了 A 车间放入产品的效率


### 单生产者-单消费者-单缓冲区-连续取出问题

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250722190116.png)
有两个同步问题：

（1）缓冲区的空闲资源必须存在，生产者才能放入资源到缓冲区中
（2）缓冲区必须有产品资源存在，消费者才能从缓冲区取走产品

有两个互斥问题：

（1）生产者和消费者对临界区的访问必须是互斥的
（2）生产者之间在某个进程连续取 10 件的其间是互斥的

所以信号量：

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250722191303.png)


生产者的代码写法与经典的完全一样：

```c
void producer() {
    while (true) {                       // 生产者循环
        生产一个产品(数据);               // 生产数据（非临界区操作）
        p(empty);                        // 请求空缓冲区（若无则阻塞）
        p(mutex1);                        // 请求进入临界区（互斥访问缓冲区）
        将产品(数据)放入缓冲区;           // 临界区操作：数据放入缓冲区
        v(mutex1);                        // 释放临界区
        v(full);                         // 增加一个产品（唤醒等待的消费者）
    }
}
```

这里消费者之间也用了一个锁 turn_lock

其实关于互斥问题，更进一步的理解是保证

```
void consumer() {
    while(true) {
        // 申请连续取特权（整个10次操作独占）
        P(turn_lock);
        
        for(int i=0; i<10; i++) {
            P(full);        // 确保有产品
            P(mutex);       // 申请缓冲区锁
            取出一个产品;    // 临界操作
            V(mutex);       // 释放缓冲区锁
            V(empty);      // 释放空槽
        }
        
        // 释放连续取特权
        V(turn_lock);
        
        // 可在此处消费10个产品（非临界区）
    }
}
```


### 读者 - 写者问题（读者优先）

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250814172220.png)

也就是允许多个读者可以同时读，但是只能有一个写者进行写操作

这个问题需要一个变量 count 来记录访问文件的读者的数量，并且此时 count 也变成了临界资源，需要互斥访问

另外一个互斥关系是写者和读者写者的文件访问互斥

这里没有同步关系，count 变量是用来处理这里的条件关系的，他不是互斥量

因此就是两个互斥信号量：

```
semaphore mutex = 1;//用来对count 进行互斥访问
semaphore mutexSW = 1;//用来写者与读者和写着进行互斥访问文件

int count = 0;//用来记录访问文件的读者个数
```

首先，读者进程在读文件之前需要修改 count 变量的值，所以会在 reading 操作前后进行互斥修改 count 变量：

```c
reader(){
	P(mutex);
	count ++;
	V(mutex);
	
	reading;
	
	P(mutex);
	count --;
	V(mutex);
}
```

然后是读者与写着的互斥问题，这里需要用到信号量 mutexSW，这个信号量的 PV 操作不能简单加到 reading 的前后，因为如果这样做了，那么读者之间也变成互斥访问文件了，这个与题意不符，所以这里也就是 count 变量的作用了，为了保证读者与写者进行互斥，用 count 变量来判断此时是否可能有写者访问文件：

```
reader(){
	P(mutex);
	//如果此时文件区没有读者，说明此时写者可能访问文件，此时需要进行互斥
	if(count == 0){
	//count用来表示当前有多少个进程在读，如果是第一个进程的话，此时还没读呢，所以if语句应该放在count ++前面
		P(mutexSW);
	}
	//如果此时文件区有读者，说明不可能写者正在访问文件，那么此时读者直接修改count进入文件区即可	
	count ++;
	V(mutex);

	reading;

	P(mutex);
	count --;
	//如果是最后一个进程，此时进程都读完了，所以if应该放在count--后面
	if(count == 0){
		V(mutexSW);//最后一个读进程走的时候才会解锁，此时允许写进程进去写数据
	}
	V(mutex);
}
```


简而言之，就是第一个读进程敲门要读的时候会加锁，这样其他的读进程可以来读文明，但是写进程不行

等到所有的进程读完之后，某个进程发现自己是最后一个读的进程，这个时候才会解锁，允许写进程进来写数据

**第一个读进程来的时候要加锁，最后一个读进程走的时候要解锁**

对于写进程来说，他不需要通过 count 变量来判断文件里面是否有读进程或者写进程，他统一用 mutexSW 这个互斥信号量来判断，因为第一个进程进去的时候会加锁，这样写进程再 P (mutexSW) 就知道有读进程在文件里面了，最后一个读进程走的时候解锁，这样写进程就可以用不必卡死了

同时写进程之间也可以用 mutexSW 这个信号量来完成互斥操作，因此写进程就非常简单了，只用 mutexSW 即可

```
write(){
	P(mutexSW);
	
	writing;
	
	V(mutexSW);
}
```

### 读者 - 写者问题（写者优先）


![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250814172220.png)

也就是允许多个读者可以同时读，但是只能有一个写者进行写操作，除此之外

上文的读者优先，如果一直有读者来读的话，这就会导致先到来的写者一直等待读者读完，这就可能导致写者被饿死

要想让写者优先，那么就需要做到，当一些读进程在读的时候，如果此时来了一个写进程，这个写进程会被阻塞，然后写进程后面再过来的读进程，他们必须要等到写进程写完之后再进行读

也就是说，在写进程之前到来的读进程可以进行读，而写进程来了之后同样会等他们退出文件，但是在写进程后面来的读进程，必须等到写进程写完之后才能进行读

要想做到上面类似的排队功能，这里必须要用到另外一个信号量 mutexQ

这个信号量的初值和 PV 操作位置直接当个结论记住，这里只分析他是怎么实现满足题意操作的

```
reader(){
	P(mutexQ);//最开始加上一个P操作
	
	P(mutex);
	if(count == 0){
		P(mutexSW);
	}
	count ++;
	V(mutex);
	
	V(mutexQ);//reading之前加上一个V操作
	
	reading;

	P(mutex);
	count --;

	if(count == 0){
		V(mutexSW);
	}
	V(mutex);
}
```

```c
writer(){
	P(mutexQ);
	P(mutexSW);
	
	writing;
	
	V(mutexSW);
	V(mutexQ);//这里V(mutexQ)和V(mutexSW)的位置无所谓，不过最好是对称写，PV操作将里面的东西包住
}
```

对于连续的读进程来说，他虽然会在最开始 P (mutexQ) 上锁，导致其他的读进程卡死在这里，但是他在 reading 之前会开锁，这样其他的读进程同样可以被唤醒进入文件进行同时读，并不违反允许多个读进程同时读文件的要求

对于写进程来说，考虑先来了几个读进程，在来了一个写进程，再来了一个读进程的情况

这些先到的读进程会进行 P (mutexSW) 操作，这样写进程就无法进入文件写了，但是写进程可以通过 P (mutexQ)，因为这些读进程会在读操作之前释放 mutexQ 信号量，此时写进程会卡死在 P (mutexSW) 而不是 P (mutexQ)

对于写进程之后到来的读进程，由于写进程进行了 P (mutexQ) 操作，所以这些读进程会卡死在最开始的 P (mutexQ) 上，这些后到来的读进程只有等到写进程写完之后进行 V (mutexQ) 操作释放 mutexQ 变量，此时这些读进程才能继续进行然后读文件

这样就实现了比写进程后来的读进程一定在写进程之后进入文件的要求了，写进程就不会被饿死了

### 哲学家进餐问题

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250816132110.png)

![image.png](https://typora-1310242472.cos.ap-nanjing.myqcloud.com/typora_img/20250816132747.png)

在哲学家问题中，如果所有的哲学家，比如上图的 5 个哲学家都同时拿了自己左边的筷子，那就会陷入死锁状态，谁也不能吃饭

我们要做的就是解决这类死锁的问题，这类问题有三种解决方式

==（1）最多只允许有 n - 1 名哲学家同时拿左边的筷子==

其实也就是只有 n - 1 个哲学家可以获得拿筷子的资格

这里用一个 count 来表示获取左边筷子的资格这样一个资源存在，在这个问题中，count 的初始值就是 4，只有前 4 个哲学家才能获得拿左边筷子的资格

同时有 5 根筷子，每 根筷子对应了相邻的两个哲学家，这两个哲学家访问这个筷子是互斥的

```
semaphore count = 4;
semaphore chopsticks[5] = {1, 1, 1, 1, 1};
process(){//第i个哲学家
	while(1){
		P(count);
		P(chopsticks[i]);//拿左边的筷子
		P(chopsticks[(i + 1)%5]);//拿右边的筷子
		eat;
		V(chopsticks[i]);//释放左边的筷子
		V(chopsticks[(i + 1)%5]);//释放右边的筷子
		
		V(count);//释放获得左边筷子的资格
	}
}
```

在这种情况下，一个极端的情况是有 4 个哲学家同时拿了左边的筷子，最后一个哲学家无法获得左边的筷子资格，被卡死在 P (count) 上面

此时会有一个哲学家可以获得 2 个筷子，可以进餐，他可以释放筷子资源，别的哲学家也可以进餐，这样就不会死锁了

==（2）仅当哲学家两边的筷子都可用的时候，才允许他进餐==

换句话就是，在同一时刻只能有一个哲学家可以拿筷子，他拿筷子的动作不可以被打断，相当于将哲学家先拿做筷子再拿右筷子当作了临界区

**让进程一口气获得所有的资源，这个思想更常用一些**

```
semaphore mutex = 1;
semaphore chopsticks[5] = {1, 1, 1, 1, 1};
process(){//第i个哲学家
	while(1){
		P(mutex);
		P(chopsticks[i]);//拿左边的筷子
		P(chopsticks[(i + 1)%5]);//拿右边的筷子
		V(mutex);
		
		eat;
		
		V(chopsticks[i]);//释放左边的筷子
		V(chopsticks[(i + 1)%5]);//释放右边的筷子
		
		think;
	}
	
}
```

==（3）奇数号哲学家只能先拿左边筷子，偶数号哲学家只能先拿他右边筷子==

这个解决思路不是特别容易想

这里将哲学家左边筷子的编号当作哲学家的编号（上文也是这样），奇数号哲学家先拿左边筷子，再拿右边筷子；偶数号哲学家先拿右边筷子再拿左边筷子，这里认为所有哲学家面向餐桌，读者看到的哲学家左边的筷子就是左（上文也是这样）

```
semaphore chopsticks[5] = {1, 1, 1, 1, 1};
process{//第i个哲学家
	//这个是奇数号哲学家
	if(i % 2 == 1){
		P(chopsticks[i]);//拿左边的筷子
		P(chopsticks[(i + 1)%5]);//拿右边的筷子
		eat;
		V(chopsticks[i]);//释放左边的筷子
		V(chopsticks[(i + 1)%5]);//释放右边的筷子
	}
}

process{//第i个哲学家
	if(i % 2 == 0){
		P(chopsticks[(i + 1)%5]);//拿右边的筷子
		P(chopsticks[i]);//拿左边的筷子
		
		eat;
		V(chopsticks[i]);//释放左边的筷子
		V(chopsticks[(i + 1)%5]);//释放右边的筷子
	}

}
```

在这种情况下，所有奇数号的哲学家都拿起左边的筷子之后，偶数号哲学家是无法拿起筷子的，于是一定有哲学家可以进餐，他释放了资源之后就不会死锁了

```C
	从B的信箱种取出一个信件;
	V(mutexB);
	V(emptyB);//B取出一个信件，会生成一个空闲资源
	
	P(emptyA);//B放入一个信件到A信箱会消耗一个A的空闲资源
	P(mutexA);
	将新的信件放入A的信箱;
	V(mutexA);
	V(fullA);//B放入A的信箱会生成一个A的信件资源

}
```

这是一个读者写者问题，三个全局变量看成三个临界资源，分别进行分析

对于变量 x，只有进程 1 读，所以不用互斥关系

对于变量 y，进程 1 读，进程 2 读，进程 3 写，这是一个读者写者的互斥关系，允许多个进程读，允许一个进程写

对于变量 z，进程 2 读，进程 3 写，这就是一个普通的互斥关系

==（1）第一种做法，保证只有 n - 1 个哲学家可以获得拿筷子的资格==

所以设一个 count 变量，作为拿筷子资格资源的存在，其值设为 n - 1

然后碗资源是另一个资源，你把这个资源加入到这个问题中就行了

```
semaphore count = n - 1;
semaphore chopsticks[n] = {1,1,1...1};
semaphore bowl = m;

process{
	P(count);
	P(chopsticks[i]);
	P(chopsticks[(i + 1)%5]);
	P(bowl);
	
	eat;
	V(bowl);
	V(chopsticks[(i + 1)%5]);
	V(chopsticks[i]);
	V(count);
}
```

或者另一种思考方式，这里将碗可以作为 count 变量来对哲学家进行限制

不过这里的碗的个数是 m 个，需要对 m 的大小进行一个分类讨论

如果 m <= n - 1，那此时可以直接将 bowl  = m作为 count 变量来使用，这些哲学家先拿碗再拿筷子，这样就可以保证不会有 n 个哲学家同时拿到左边的筷子了，这里的碗就和上文中的资格是作为相同功能的资源，让这些哲学家先拿碗再拿筷子，同样不会出现 n 个哲学家同时拿到左边筷子的情况死锁出现

如果 m > n - 1，即 m >= n，那此时碗这个资源在这个题目中就是多余的，反正每个人都可以分配到一个碗，他同步同步互不互斥就是无所谓的，那此时 bowl 这个变量就当作 count 变量来用，设置成 n - 1，退化成了普通的哲学家问题

将这两种情况综合一下，于是可以将 bowl 变量设置成 min (m, n - 1)，那么无论哪种情况都可以满足了

这里将碗作为资格的原因主要是哲学家在吃饭的时候一定是碗和筷子同时存在的，同理上文中用资格来限制的时候哲学家在吃饭的时候一定是资格和筷子同时存在的，所以就可以将碗作为资格就可以了
